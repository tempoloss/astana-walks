# Источники геоданных по Астане (разведка 2026-10-16)

Всё проверено живыми запросами, кроме помеченных. Ничего из 2GIS — по их ToS парсинг/хранение запрещены.

## 1. OpenStreetMap (основа, уже используем)
- **Overpass API** — то, что делает `overpass_poi.py`. Легально: ODbL, нужен UA и умеренность (у нас есть).
- **Geofabrik extract**: `https://download.geofabrik.de/asia/kazakhstan-latest.osm.pbf` — 214 МБ, обновлён вчера (проверено заголовками). Есть `kazakhstan.poly` (граница), shortbread `.mbtiles`, shapefile/gpkg-бандлы. Даёт ВСЮ страну разом: дороги, здания, public transport (route=bus, остановки), границы районов — без нагрузки на Overpass. Фильтровать `osmium clip`.
- **Nominatim** (геокодинг по адресам) — демо работает, Бәйтерек находится по-русски (проверено). 1 req/s, UA обязателен.

## 2. Национальный геопортал map.gov.kz (WFS, без ключей!) ✅ проверено
GeoServer, стандартный OGC WFS 2.0, JSON отдаёт сразу (`outputFormat=application/json`):
```
https://map.gov.kz/geoserver/ows?service=WFS&version=2.0.0&request=GetFeature
  &typeName=openmap:buildings_a&count=100
  &bbox=71.35,51.05,71.50,51.15,EPSG:4326&srsName=EPSG:4326&outputFormat=application/json
```
Слои (66 тайтлов, полный список в GetCapabilities; счётчики пересняты 2026-10-17 по bbox 71.1–71.9/50.9–51.4 через `resultType=hits`):
- `openmap:buildings_a` — **171 235** полигонов зданий с `levels`, `usage`, `material`, `area`, `addr_str/addr_num` (проверено);
- `openmap:roads_l` — **8 861** линий с `str_name` (названия улиц) и `class` (проверено);
- `geonode:border_districts` — **40** полигонов районов, в т.ч. Астана — это СЛОЙ РАЙОНОВ; `geonode:orda_kato_wgs84` по этому bbox ПУСТО (0; его фичи — Аральский район, проверено);
- `geonode:funk_zonning_4v`, `master_site_4v`, `razgraf_*` — функциональное зонирование, генпланы, разграфка;
- `geonode:kokterek_*`, `mortyk_*`, `tleusay_*` — детальные микрорайоны Алматы/Туркестана (не Астана).
Нюансы запросов: `count=0`+bbox этот GeoServer ломает (пусто при 171k совпадений) — считать `resultType=hits`, листать `maxFeatures`/`startIndex`; `cql_filter` → HTTP 500, серверной фильтрации по атрибутам нет.
Лицензия — госоткрытые данные РК (AccessConstraints/Fees в DescribeFeatureType — NONE).

## 3. data.egov.kz (официальные открытые данные акимата)

- **Но есть keyless-эндпоинты самого портала (проверено 2026-10-17, раунд 2): `/datasets/getmeta?index=<slug>` (схема/владелец/дата) и `/datasets/exportjson?index=<slug>&version=<v>&from=N&count=100` (реальные строки, кэп 100/запрос, `version` из JS страницы) — ключ не нужен.** См. §11.
- Хозяин «Астана қаласы әкімдігі»: школы, детские сады, поликлиники, маршруты автобусов (`kalalyk_avtokolik_bagdarlary` — но в архиве с 2020, проверено на странице датасета). В записях поля `latitude`/`longitude`/`street`.

- Реестр датасетов: фильтр по органу «Астана қаласы әкімдігі» на сайте.

## 13. Факты с официальных сайтов заведений (2026-10-17; `collect/sites/`, `data/sites/facts/*.json`)
Часы, адрес, телефон и (где сайт сам их печатает) координаты берутся **только со страниц самих заведений** —
не 2ГИС/Яндекс/Zoon/соцсетей (их ToS запрещают хранение или требуют логин: `domains.BLOCKED_DOMAINS`). Метод: инвентарь
доменов по POI (`inventory.py`, 300 доменов + ручные цели), краулеры по доменам (JSON-LD, JSON локаторов, текст
страниц), каждый факт хранится с `evidence` — дословный фрагмент страницы (≤ 300 символов) и URL; `verify.py --write`
удаляет факт, чей фрагмент не находится в кэшированной странице, и филиалы с координатами вне Астаны.
Юридически: это факты о самом бизнесе с его собственных публичных страниц, `robots.txt` соблюдается (`robots_ok:
false` ⇒ ветки не сохраняются; ≤ 1 запрос/с на домен), страницы кэшируются, не копируются целиком. Часы без дней и
`00:00-00:00` без «круглосуточно» не превращаются в `opening_hours` (`hours_unqualified`).

Итог (313 доменов, 106 с филиалами; 432 проверенных филиала, все фрагменты найдены: 1710/1710; 129 доменов закрыты
robots.txt; 282 филиала с OSM-часами, 41 текст «без дней», 4 неоднозначных 24 ч; 228 с координатами с самого сайта).

### 14.4 Оценки (дыра ratings=0) — жёсткий вывод: легально ХРАНИТЬ нечего

Ни один провайдер с реальными астанинскими рейтингами не разрешает их хранить. **OSM `rating`/`stars` в Астане = ровно 9 объектов, все звёздные классификации отелей** (Hilton 5, Rixos 5, Hampton 3), пользовательских оценок заведений 0 (Overpass `out count`: nodes 6/ways 2/relations 1); при этом **категории `hotel` в рекомендованном наборе вообще нет** (`data/poi_enriched_stats.json` `count_per_category`) ⇒ даже эти 9 звёзд дыру не затыкают: ratings остаётся 100 % открытым. Geoapify «cache/store results with no limits» и LocationIQ «store response data forever» — хранилище разрешают, но это OSM-дериват без рейтинга. Restaurant Guru (`5, 1736 votes`) — «personal use», скрейпинг запрещён → DEAD. TripAdvisor Terra — «caching … storing … not permitted», только location_id. **Рекомендация: колонку рейтинга в БД НЕ вводить; ранк-тайм подстановка Google Place Details Enterprise $20/1k (1000 бесплатных/мес) — один вызов даёт rating+priceLevel+regularOpeningHours+userRatingCount сразу (закрывает и дыру цен); дешёвый фолбэк TripAdvisor 5000 бесплатных/мес.** Оговорки честности: **покрытие КЗ этими API не измерено** — перед покупкой мерить долю непустых rating на выборке из 2316 POI по ключу, иначе повторится KFC-скос (цепочки оценены, независимые места — нет); экономика на питч: ~3 вызова detail на запрос ⇒ 1000 DAU × 3 запроса ≈ 9000 вызовов/сут ≈ $180/сут ≈ **$5 400/мес** только за рейтинги (при $20/1k), плюс runtime-зависимость ломает `WALKS_OFFLINE=1` (хранить ответ нельзя — только сессия). Единственная оставшаяся надежда на STORE-рейтинг (не проверено): `aggregateRating` JSON-LD на собственных сайтах заведений — для ответа нужен повторный обход ~313 доменов (`collect/sites` сырой HTML не хранит, `grep aggregateRating` по `data/sites/` = 0); самопровозглашённые оценки — маркетинг, в ранжирование их не пускать, только `field_sources.official_site`.
**Уточнение раундом 7 (§17.1, retention-оговорки платных тарифов прочитаны дословно):** вердикт «не хранимо» подтверждён на первичных текстах — Foursquare PAYG «no caching permitted», HERE 30 дней, Mapbox «shall not store … Temporary Geocodes», Yelp 24 ч + запрет «create your own database». Хранение разрешают лишь Stadia ($80/мес)/Geoapify/OpenTripMap, но ни у кого в выдаче нет рейтинга/часов (только OSM-поля). **Две новые развилки:** (1) flat-file **Foursquare Places Premium** открыто ПРОДАЁТ `rating`+`hours`+`photos`+`price` аддоном к страновому пакету ⇒ CONTRACT-путь к легальному хранению (цена непублична, «Early Access Only»); (2) runtime-опция **Foursquare Premium API ≈$1 687/мес** дешевле зафиксированной выше Google-оценки при том же наборе полей. Плотность рейтингов по КЗ у обоих по-прежнему `[не проверено без ключа]` — мерить на всех POI текущей базы (`after.total` в `data/poi_enriched_stats.json`) до покупки. Рекомендация не меняется: колонку рейтинга в БД не вводить.

### 14.5 Новые STORE-источники POI/адресов/часов (сверх раундов 1–3)

Два недокументированных фронт-энд эндпоинта без ключа: `GET /datasets/getdatasetsre?page=&count=10&byGovAgencyId=<id>&status=PUBLISHED` + `/getdatasetsrecount` (обход всего каталога; **3944 набора, у Акимата Астаны `byGovAgencyId=AVUvu_Wu99eXTcgzf9td` ровно 52**), и **`/datasets/exportjson?index=<slug>&from=&count=`** — `version` **необязателен** (проверено дважды: `version=v14` и без него отдают одинаковые строки; пустой ответ `[]` даёт только выдуманное значение вроде `version=1` — раньше на этом и спотыкались, принимая `[]` за пустой датасет). ⚠️ **`from` — 1-базированный номер первой строки** (`from=0` и `from=1` идентичны; `from=100&count=2` → id 100,101): шагать `from=1,101,201…` и дедупить по `id`, иначе пограничная строка дублируется на каждой странице. ### 14.6 UGC / «город в реальном времени» (слой отметок)

Единственный высокоурожайный внешний канал — **публичные Telegram-каналы через серверный HTML `https://t.me/s/<username>` без авторизации**: `@astana_newss` (1.78K подписчиков, название «Astana news» — ⚠️ это НЕ пресс-служба акимата, официальным каналом акимата в деке называть только gov.kz `org/astana-madeniet`/`org/astana`; фид полезный: ярмарки/закрытия/открытия), `@qr_tjm` «112 KZ» МЧС (33.2K — шторм/Дармен), `@sxodim_astana` (17.4K — афиша), `@tengriastana` (12.5K). Механика поллинга: /s/ отдаёт последние ~20 постов, пагинация `?before=<post_id>`, заметная доля постов — медиа без текста (`text_not_supported_wrap`) ⇒ фактов на fetch меньше 20, дату брать из `<time datetime>`. ToS Telegram + авторское право владельца ⇒ **хранить только извлечённые факты + deep-link `t.me/<chan>/<id>` + «Источник: @chan»**, полные тексты/медиа не копировать; в API ToS §1.5 дословно запрещён «using, accessing or **aggregating** data obtained from the Telegram platform» для обучения/развёртывания ИИ — живой риск, если позже захотим файнтюнить на подписях постов. **Сигнал состояния города с чистой лицензией: OSM Notes** (`api.openstreetmap.org/api/0.6/notes/search?bbox=…&closed=0`, ODbL в шапке ответа) — ⚠️ замер второй нитью: 9 открытых нот в bbox (живой `closed=0`-запрос раунда 4, другой день/шире bbox; в снапшоте 17.10 на одной странице — 7, см. ниже), но свежие (12.10) — железнодорожный/мапперский трафик («Перешивка на 1 линию», запросы новых POI), авто-репорт Organic Maps «заведение исчезло» от 27.06; плотность единиц в квартал ⇒ бесплатный еженедельный поллинг, а не опора фичи. **OSMCha changesets** (нужен OSM-OAuth токен; детектор стройки/сноса) — нагрузка здесь выше. Google Maps/2GIS/IG/FB/VK/Reddit/Waze — не хранимы (Reddit §3.1 — отдельный коммерч. договор; Waze for Cities — agency-only, «prohibited … for any commercial purpose»; Meta Content Library — for-profit ineligible). e-Otinish/iKOMEK — per-appeal API нет (только квартальные агрегаты на egov).

**Слой «живо ли место» из самих OSM-заметок — УЖЕ В ПРОДЕ** (`collect/city/notes.py` → `data/city/osm_notes.json`, потребитель `app/walks/city_layers.py`, страница «Города», ODbL, без ключа). Измерено по shipped-снапшоту 17.10: страница из **300** последних обновлённых заметок bbox'а Астаны: `open` **7**, `closed` 293; классификация: `closure` **60**, `new_place` 11, `construction` 4, `hours` 2, `other` 223. Две правки против прежних формулировок: **(а)** «за последние ~45 дней» было ложью — `closed=-1&limit=300` не фильтрует по дате, `date_created` в снапшоте **2016-06-02…2026-10-12**, а `CLOSED_DAYS=45` лишь писался в meta и никогда не применялся (исправлено в этом же коммите: meta-ключ → `page_limit`/`window`); **(б)** как следствие `notes_open: 7` — **нижняя граница**, а не счётчик: заметка, открытая в 2017-м и с тех пор не тронутая, в 300 последних обновлённых не поместится (граница страницы измерена: min last-touched на снапшоте = **2025-04-10**, за борт попадают только открытые, которых не трогали с ≤2025-04; в окне 2025-04→сегодня других открытых на странице нет — все 7 созданы ≥2026-06-27, так что за последние ~18 месяцев семёрка это полная картина, а нижняя граница — только для более старого хвоста). Позиционирование для жюри: это **provenance-сигнал** («на карте есть неподтверждённая жалоба — проверьте»), а не покрытие: из 60 `closure` заметная часть — авто-репорты MAPS.ME/Organic Maps, некоторые возрастом до 10 лет. **После 22.10:** пейджинг по датам (`closed=-1` + проход страниц) и отдельный проход по `USED_CLASSIFICATIONS`-лиду. **Хвост измерен 18.10 вместо оценки:** `notes/search.json?bbox=<тот же>&closed=0&limit=10000` (keyless) даёт **9 открытых по городу** против 7 на странице снапшота — ровно 2 заметки, не тронутые с ≤2025-04, то есть нижняя граница завышена на 29 %, а расхождение «9 vs 7» раунда 4 объяснено полностью (9 — и есть истина, тред-замер 4-го раунда был прав). Из 9 открытых closure-класс только 2 — coverage-проблема маленькая в обе стороны, provenance-фрейминг остаётся. Правка пост-22.10: отдельный `closed=0`-фетч для счётчика открытых (он влезает в один запрос) вместо пейджинга всего `closed=-1`; артефакт `recon/round9/notes_open_citywide.json`. Семантика `closed` проверена контрольными прогонами 18.10 (документация вводит в заблуждение): это **число дней**, а не булев флаг — `closed=0` = только открытые; `closed=1` = открытые + закрытые за сутки (у нас вернул те же 9, ложно читается как «1=только закрытые»); `closed=3650` = 9 открытых + 640 закрытых за 10 лет (всего 649 — полная картина, усечения нет при limit=10000); **без параметра `closed`** ответ вернул 10 записей (9 open + 1 newest closed) **даже при явном `limit=10000`** (воспроизведено 18.10 дважды) — т.е. это окно по умолчанию, а не limit; механизм внутри API не вскрывали, дефолтный запрос без `closed` не использовать.

### 15.1 Главная находка: keyless-окошко `data.egov.kz/api/detailed/<index>` + адресный реестр RCA
`GET https://data.egov.kz/api/detailed/<индекс>?source={<Elasticsearch DSL>}`, **без apiKey** (в отличие от `api/v4` = 403), нужен UA + `Accept: application/json` (в curl — `--globoff` из-за скобок). Открывает то, чего раунды 1–4 не видели:
- **Адресный реестр РК (ИС «Адресный регистр»/RCA, Комитет по правовой статистике Генпрокуратуры).** `s_buildings,s_grounds_new,s_pb` match_all = **9 900 613** записей по стране. Точный срез Астаны (не `match`!): 6 районов через `terms s_ats_id ["107989","108584","252205","252235","251449","107193"]` → **85 256 адресных строк**; `s_geonims` тем же срезом = **4032 топонима, из них 3016 тип 11 «УЛИЦА»** (+ словарь `d_geonims_types`, 85 кодов: бульвар/площадь/проспект/переулок/микрорайон/жилмассив… с казахскими аббревиатурами `көш.`, `даңғ.`). **`max(modified)` = 2026-10-15** ⇒ реестр живой (против OpenAddresses ≤2017 — теперь это наш основной источник названий/иерархии/алиасов; исторические имена города Акмола/Целиноград/Нур-Султан идут бесплатным алиас-слоем). Отдельных координат в `s_buildings` **нет** (есть `rca`, `post_index`, `cadastre_number`) ⇒ сам по себе не геокодер; мост к координатам даёт `ERSOP_OBJ` (§15.8) — **проверено основной нитью: 3/3 взятых астанинских RCA из `ERSOP_OBJ` резолвятся в `s_buildings` термом `{"term":{"rca":…}}` на тот же адрес** (ключ exact, не fuzzy), но RCA-код есть не у каждого объекта/POI ⇒ это частичный, а не полный мост. Правовой режим как у всех госданных РК — № 401-V ст.1 п.5; явной лицензии на `/api/detailed` нет, рекомендуемая атрибуция правообладателя («Комитет по правовой статистике … Генпрокуратуры РК») — **добрая воля, не опубликованное требование** (обязательной формулы в законе нет, §14.0/B5).
- **Координатные гос-реестры того же API** (в отличие от RCA — с `geoposition`!): `pharmacy` → 56 (из них 53 Астана по `Region:17108`; строки вида `{"Name":"Гиппократ № 03","Address":"г. Астана, м-н Достык ул. Сауран д.5","geoposition":"51.121077,71.419938"}`); `notaries` → 746 нац. (гео+телефон, но `Region` НЕ 17108 — кодовая сетка отличается от pharmacy, резать по тексту адреса); `ps_centers` → 555 ЦОН нац. ⚠️ **Витрина, а не реестр**: контроль OSM `amenity=pharmacy` в том же bbox = **182 узла**, т.е. покрытие аптечного индекса ≈29 %; полнота notaries тоже не доказана (нотариусов в РК заведомо больше). Ценность — валидация имени/адреса/координат УЖЕ имеющихся POI, а не «покажем все аптеки рядом». Индексы недокументированные: список не перечисляется (`_cat/indices` заблокирован), доступ по угаданному slug, явной лицензии нет (правовая база — № 401-V ст.1 п.5, атрибуция правообладателя по доброй воле) ⇒ статус «проба перед загрузкой», хост может закрыться без уведомления.
- **Версионный индекс = сигнал изменений реестра, не фид закрытий.** `/api/detailed/madeniet_uiymdary/v17` (13 строк, казахские названия) против v2 (6) / v1 (9). Дифф живьём: исчезли «Дворец Независимости», «Дворец Мира и Согласия», «Астана-Байтерек»; добавились «Дирекция объединённых музеев», ТЮЗ им. Мамбетова, «Театр кукол», «Столичный цирк»; переименована филармония (→ им. Еркегали Рахмадиева). Три оговорки, иначе механизм врёт: (1) исчезновение ≠ закрытие — реестр пересобирается по типу собственника (ГККП/КГУ/ТОО), «Астана-Балет» пропал именно так ⇒ пользователю «закрыто» показывать только после ручной верификации; (2) схемы полей различаются по версиям ⇒ матчить по id+имени, не по колонкам; (3) **несуществующая версия (`v99`) отвечает `[]`, неотличимо от пустой ⇒ перебор v1..vN вслепую запрещён**; текущую версию брать из `currentVersion = 'v17'` на странице датасета (проверено основным нитью), в `getmeta` поля версии нет.

Годов в бакете: 2018, 2019, 2022–2025 — **пропуск 2020–2021 и 2026 нет** ⇒ это 7-летняя эталонная базовая линия «сегодня хуже обычного», вычисленная локально из public domain, а не живой AQI.

### 15.5 Фото (дыра photos≈0): реалистичный потолок ~90–100 карточек, а не на всю базу
- **Wikimedia Commons `geosearch` вокруг координат POI** — проверено основной нитью: `ggscoord=51.1282|71.4305 & ggsradius=300 & ggsnamespace=6 & prop=imageinfo&iiprop=url|extmetadata` → **50 файлов** вокруг Байтерека (потолок `ggslimit`, не истинное число), в каждом `LicenseShortName` («CC BY-SA 3.0», «CC BY 2.0»), `Artist`, `AttributionRequired:true` ⇒ полный атрибуционный конверт в одном JSON. ⚠️ Близость ≠ изображение объекта: первые хиты — «New buildings in Astana2.jpg» и общий вид ⇒ нужен gate релевантности (имя POI или его Commons-категория в заголовке; приоритетные семена — тег `wikimedia_commons=` и Wikidata `P18`), иначе карточка Байтерека получит стройплощадку — хуже, чем фото без него. `AttributionRequired` хранить пофайлово, кредит печатать только где true (CC0-файл Astana Opera кредита не требует). Hit-rate: музеи/парки/памятники ~0.5–0.7 (оценка по двум пробам), **кафе/рестораны/площадки ≈ 0**.
- **Openverse API** (`api.openverse.org/v1/images/?q=<имя>&license=by,by-sa,cc0,pdm`) — landmark-запросы дают Bayterek 71 / Khan Shatyr 119 / Astana Opera 53 / Nur Alem 8 CC-изображений с готовым полем `attribution`; anon-лимит 20/мин, 200/сут ⇒ ~1.5 дня на 300 landmark-запросов. Кафе-запросы (`astana cafe`) = 1 нерелевантное.
- OSM-теги картинок почти пусты: `image=` 3 объекта (ссылки на новостные сайты — не лицензионные), `wikimedia_commons=` 2 (полезные категории). Unsplash/Pexels/Pixabay — ключ + «no bulk», Mapillary — CC BY-SA + Meta ToS (не хранить), логотипы сетей = trademark (только показ, не редистрибуция). Итог: STORE-пайплайн = Commons-geosearch по wdid/координатам (атрибуция в `field_sources`) + Openverse-дополнение; **потолок ~90–100 знаковых мест, у кафе фото берём с их же сайтов (`collect/sites`)**.

### 15.6 Юр. аудит переносчиков вывода (то, что не читали в раунде 4)
- **Gemini API**: на **бесплатном (Unpaid) tier** «Google uses the content you submit … to … improve its products» + «**Do not submit … personal information to the Unpaid Services**» — а у нас free-text пользователя ⇒ на проде обязателен **Paid tier** (привязка биллинга; «Google doesn't use your prompts … to improve our products»). Плюс «You must be 18+ … not … likely to be accessed by individuals under 18» → нужен 18+ дисклеймер в UI. Обязательного бейджа «Generated by Gemini» нет; достаточно не выдавать ИИ-текст за человеческий (Prohibited Use).
- **OpenAI**-совместимый канал (`chat/completions`, у нас есть в цепочке): «data sent to the OpenAI API is **not used to train** … unless you explicitly opt in» ⇒ безопасно по умолчанию, ZDR не нужен (ПД в промпте нет). **AlemLLM** (`llm.alem.ai`, профиль ALEM) — условия хранения/обучения/лицензии **не опубликованы** (только интеграция на doc.alem.ai); вероятно KZ-инфраструктура (плюс к ст.12), но письменных гарантий нет ⇒ запросить перед прод-зависимостью.
- **CC BY-SA через LLM**: факты (название/адрес/часы/координаты) не охраняемы ⇒ не Adaptation; пересказ охраняемого wiki-текста = Adapted Material → показывать со ссылкой + SA-строкой (одна строка в карточке/футере закрывает §3(a)(1)/§3(b)); в RK нет sui generis права на БД, «substantial portion» вики-базы мы не копируем ⇒ весь продукт открывать не надо.
- **Персональные данные РК (94-V), важное открытие:** «перечня государств с адекватной защитой» постановлениями Правительства **не существует** (это конструкция РФ; ст.16/26/27-1 94-V такого акта не предусматривают) ⇒ легальный путь трансграничной передачи — **отдельное согласие субъекта (ст.16 п.3)**. Действующий демо-VPS за рубежом ст.12 **не** нарушает, т.к. мы не храним ПД (округлённые координаты без идентификатора = обезличенные по ст.1). Соло-ИП = субъект МСП ⇒ уведомления уполномоченного органа (ст.10-1, ред. 2026) не требуется. Чек-лист согласия ст.8 п.4 из 8 пунктов зафиксирован в `scout5_commercial_terms.md`.
- **Зависимости UI чистые**: Streamlit-библиотека Apache-2.0 («The Software is not governed by the below terms»), но **Community Cloud — только non-commercial** ⇒ прод на self-host VPS. FastAPI/folium MIT, весь остальной стек (pydantic/httpx/rapidfuzz/google-genai/uvicorn…) — permissive, **GPL в `pyproject.toml`/`uv.lock` нет**. Font Awesome (folium `prefix="fa"`) Free = CC BY 4.0 / MIT / OFL — OK с одной credit-строкой; лимит 10k относится только к Kit'ам.

- **ЕРСОП — «Единый реестр субъектов и объектов проверок» (Комитет правовой статистики): единственный датасет за 5 раундов с ЯВНОЙ лицензией и рабочей связкой до карты.** Реестровый аспект Магды (`magda-ds-faa0e99e-…`) отдаёт 7 дистрибутивов с дословным `"license": "For general re-use (Creative Commons CC BY4.0)"`; реестровые `downloadURL` (`magda-minio-web…`) = 404, рабочий хост **`s3.sdu.gov.kz/magda-datasets/…`** (переезд как у ЕГКН), часть файлов — **xlsx с inlineStr** (`ERSOP_OBJ.xlsx` 31.4 МБ, `GET_CHK.xlsx` 9.0 МБ, `CHK_LIST.xlsx` 12.5 МБ). Измерено основной нитью: `ERSOP_OBJ.xlsx` = **135 149 строк, из них 10 624 по Астане (счёт по подстроке «Астана/Нур-Султан» в `ADDRESS`, не точный админ-разрез)**, поля `ID, SBJ_ID, NAME_RU, NAME_KZ, REG_ID, LOCALITY, STREET, BUILDING, ADDRESS, ADDRESS_KZ, RCA, STATUS, COORDINATE_X, COORDINATE_Y`; координаты — **EPSG:3857 Web Mercator** (7950395/6651471 → 71.47E/51.16N, обратный пересчёт — 4 строки кода, без pyproj/зонной неоднозначности). Связка проверок: `ERSOP_PROD_CHK_LIST_FC.csv` → `OBJ_ID` резолвится в `ERSOP_OBJ.ID` **200 001 из 200 001** (14 081 — Астана); плюс **мост `RCA` → адресный реестр (см. 15.1) 3/3 резолвится** ⇒ цепочка «нарушения → объект (имя/адрес/координаты) → карточка POI» exact-ключом, БИН не нужен (моя ранняя формулировка «упирается в БИН→адрес» снята). Оговорки (все обязательны перед загрузкой): (1) `*_FC` — ежедневные снапшоты, один `ID`/`CHK_LIST_ID` повторён на каждую `SDU_LOAD_DATE` ⇒ без дедупа по бизнес-ключу + последнему load метрики завышены ~×30 (скан 4 М строк CHK_LIST: загрузки 2025-01-23…2025-03-17); (2) `BIN` в `GET_CHK` — SHA-хеш 64-hex, имени субъекта («ТОО …») в 7 файлах нет, джойн только object-level (`OBJ_ID`), не business-name; (3) `NAME_RU/NAME_KZ` объектов — property-уровня («Многоквартирный ЖК со встроенными помещениями», «Уличное освещение села Батыр», «ТП №… кв №…»), т.е. это inspected premises/сооружения, карточка кафе по имени сюда не сядет — матчинг по адресу/RCA/координате; (4) даты проверок измерены min/max `DATE_BEGIN` по xlsx-выборке = **2021-02…2024-12** (загрузки до 2025-03) ⇒ **регулярно пополняемый реестр, а не «только 2021–22»; но и не live-рейтинг**; (5) кодбуков `REG_ID`/`AREA_ACTIVITY_ID`/`LIST_TYPE_ID`/`STATUS_ID`/`RESULT_CHECH_ID` в датасете нет ⇒ отображаемый сигнал = «проверялось / нарушения: да-нет», никогда не именованная разбивка; (6) 31 МБ xlsx и 1.38 ГБ csv — тяжёлая загрузка, OBJ есть только в xlsx ⇒ разовый офлайн-конверт, никогда не nightly. Итог: **STORE (CC BY 4.0 явно) — легальный исторический сигнал проверок/нарушений с адресом и координатой; закрывает §14 «никакого легального quality-сигнала нет»**, но это данные о нарушениях, не рейтинг качества.
- **Смежный вывод для слоя «город»:** джойн «адрес/координата → объект проверок» работает из того же `ERSOP_OBJ`, т.е. у нас впервые есть легальный ключ `(адрес|координата) → юридическое лицо + история проверок`. Тот же механизм закрывает и «живо ли заведение» лучше, чем OSM Notes: `STATUS` у объекта + `actual`-флаг RCA (§15.1) + версионные срезы реестров (§15.1).

### 17.2 Flat-file, который ПРЯМО ПРОДАЁТ нужные нам колонки
**Foursquare Places Premium** (датасет, не API; rendered `docs.foursquare.com/data-products/docs/places-pro-and-premium`): колонки `rating` (Float 0–10), `price`, `hours` (JSON день→[open,close]), `photos[]` — подаются как «rich attributes **available as add-ons to any standard country or region package** at an additional charge». Т.е. путь к легальному хранению рейтингов/часов/фото для КЗ существует как продукт, но: страница помечена «**Early Access Only — Fill out the Contact Us form**», публичного retention-текста flat-file лицензии нет `[не прочитано полностью]`, цена не опубликована ⇒ вердикт **CONTRACT**. Это **единственная документированная дорожка** (помимо Google/FSQ runtime), и она стоит того, чтобы написать Foursquare sales письмо: retention-права + пакет KZ + rich attributes + цена.

### 17.3 Новый легальный источник часов И цен: e-museum.kz (Министерство культуры и информации РК)
**Единственный по-настоящему новый хранимый фид часов и цен, найденный раундом** — национальный GIS музеев РК на WordPress; WP-REST открыт **без ключа**, `robots.txt` запрещает только `/wp-admin/` (проверено основной нитью 17.10; объёмы и состав астанской выборки пересчитаны мной, скаут и занижал масштаб, и завышал городскую часть):
- **Масштаб: национальный реестр, а не список города.** `GET https://e-museum.kz/wp-json/wp/v2/museum?per_page=100` → `X-WP-Total: 858` (это **записей, не учреждений**: каждый объект продублирован в kk/ru/en — поля `lang`, `translations{id}`, `original_id`) ⇒ дедуп строго по `original_id`, национальная оценка ≈ 858/3 ≈ **286 учреждений**. На странице 1 из 100 заполненность `work_hours` 100/100, `ticket_price` 100/100, `addresscity` 97/100. **Астана (`?region=3952`) распечатана целиком** → сохранено в `recon/round7/emu_astana.json`: **15 строк = 5 уникальных `original_id`, но в самом городе только 4** — `original_id:155` («Alzhir» Memorial complex) несёт `addresscity="Ақмол ауылы"`, т.е. Акмолинская область (~215 км) ⇒ **`region=` течёт и на типе `museum` тоже**, не только на `tours`: после геокодинга обязателен гейт по расстоянию/bbox, иначе прогулочное приложение посоветует музей в двухстах километрах.
- Поля записи: `title`, `content`, `work_hours`, `ticket_price`, `museum_type`, `site_info`, `logo`, `image`, `multimedia`, `is_active`, `link`, `slug`, `addresscity`/`addressstreet`/`addresscountry`/`addresspostalcode` (верхний `address` пустой, значения — в составных `addressstreet`+`addresscity`), `region[]` (id таксономии WordPress, **не КАТО**), `modified`/`date` (есть строки от **2026-10-01** ⇒ живой реестр). ⚠️ **Координат в API нет** — и ГИС-модуль их не отдаёт: тело `e-museum.kz/gis/` (7914 Б) содержит только 4 вхождения `leaflet` и ноль `arcgis|FeatureServer|geojson|/api/` (замерено grep, а не «страница 200») ⇒ машинного эндпоинта точек нет, координаты по-прежнему только геокодингом адреса (локальный Nominatim, §14.0). **Часы различаются по учреждению** (замер по 15 астанским записям): `09:00-18:00` — ВИМ ВС РК, Сейфуллин, «Алжир»; `10:00-18:00` — Национальный музей и историко-культурный музей-заповедник ⇒ поле курируемое, не шаблонный дефолт; конкретные 4 всё же сверить с официальными страницами. Дней недели нет ⇒ класс `hours_unqualified` (как весь `collect/sites`), в UI «обычно 09:00–18:00» с URL+датой, не авторитетные `opening_hours`; формат ненормализован (`9:00` vs `09:00`, точки вместо двоеточий, `от 300 тг`, `тегін/бесплатно` в поле цены) ⇒ нужен парсер+приведение с сохранением сырой строки как `evidence`. Примеры: «State Military-Historical Museum» 09:00–18:00 / 500 тг; «Museum of Saken Seyfullin» 09:00–18:00 / 500 тг; «Астана Опера» 10:00–18:00 / 1000 тг; адрес «Республики даңғылы 2», «Астана қаласы». ⚠️ **`multimedia[]`/`logo`/`image` — фотографии, принадлежащие музеям** (хостинг `crm.e-museum.kz`, лицензия в ответе не указана) ⇒ факты (`work_hours`/`ticket_price`/`address`) храним, **картинки — только по письменному разрешению**, дыру фото этим фидом не закрываем.
- ⚠️ **Ловушка фильтра (замерена основной нитью на обоих типах): `region` частично рабочий.** На `tours` он **игнорируется молча** (`tours?region=3952` → `X-WP-Total: 45` = столько же без фильтра, первая запись — тур Жамбылской области); на `museum` он работает по сути, **но пропускает чужую запись** (Акмол, см. выше). ⇒ правило для коллектора: никогда не доверять `region=` — всегда сверять (1) total с фильтром против общего и (2) `addresscity`/координату в теле ответа. Кастомные типы (`/wp-json/wp/v2/types`): `museum`, `tours`, `exhibit`, `kato`, `model_3d`, `news_article`, `social_media_link`; типов `theater`/`library`/`hall` нет (404) ⇒ **театры и библиотеки этим порталом не закрываются**. `tours` (45) = **виртуальные/аудио-туры при конкретном музее** (`museum{original_id,site_info}`, `tour-link`→`e-museum.kz/en/tours/<hash>/`), НЕ городские пешие маршруты ⇒ не сопрягается с 62 названиями маршрутов `nur-sultan_kalasy__turistik` (§16.4) и в walk-слой не идёт; максимум — deep-link + текст для RAG (авторский контент ⇒ цитатой с URL по правилу §13).
- Языковые клоны: каждая запись существует в kk/ru/en (`lang`, `translations{id,original_id}`) ⇒ **считать учреждения только после дедупа по `original_id`** (проверено: «Алжир» kk и ru несут один `original_id: "155"`), иначе любой total завышен втрое.
- Продуктовая ценность: `museum_gallery` = 25 POI с часами **8.0 %** (блок `after` → `pct_opening_hours_per_category`, shipped-база; в срезе `relevance.now` та же метрика = 4.0 % — разные множества, не противоречие) и `attraction_landmark` 2.4 %. Для текущего продукта это **+4 астанских музея с часами и ценами из 25 POI категории** (не 5: «Алжир» — Акмола), т.е. частичное закрытие, а не «дыра закрыта»; один из них (Военно-исторический) уже частично покрыт нашим `collect/sites/crawlers/e-museum.kz.py` по жёсткому URL — теперь это 1 запрос на регион. Бонусом `ticket_price` бьёт в дыру цен (раунды 1–6: ≈0), а `site_info`/`content` — в дыру описаний (авторский текст ⇒ цитатой). Национальный охват (≈286 учреждений с часами, ценами и трёхъязычными названиями) — **аргумент расширения на мульти-город** (Туркестан/Боровое из §15.3), а не сегодняшняя выгода. ⚠️ Тип `kato` зарегистрирован, но его содержимое не разобрано (`kato?search=Астана` → `[]`, поиск на нём не работает) ⇒ что `3952` = Астана, доказано **самими записями** (4 из 5 с `addresscity="Астана қаласы"`), а не словарём.
- **Правовая база и атрибуция (почему это STORE):** реестр ведётся государственный орган по ст. 23 Закона РК «О культуре» — оператор **РГКП «Национальный музей Республики Казахстан»**, куратор **Министерство культуры и информации РК**; это ведомственная публикация о собственных объектах культуры, режим повторного использования — тот же, что у прочих госданных (№ 401-V ст. 1 п. 5: свободное использование, обработка, повторная публикация и распространение); отдельной лицензии на API-ответ нет, обязательной формулы атрибуции в законе нет (§14.0/B5) ⇒ в `field_sources` пишем «e-museum.kz — Национальная цифровая платформа музеев РК (оператор — РГКП „Национальный музей РК“, МКИ РК)», URL записи (`link`) и дату среза. ⚠️ Юридическое лицо-разработчик платформы (Torus) указано только как технический интегратор, его форма собственности не подтверждена по первичному тексту — в атрибуцию не вносим. Тексты страниц `/ru/about/`, `/gis/` — авторский контент: факты из карточки (часы/цена/адрес) храним свободно, прозу `site_info`/`content` — цитатой с ссылкой.

### 17.4 Всё остальное из «ищем часы» — закрыто перебором
- Ни один «opening_hours resolver» API не существует как фид: `openingh` — JS-библиотека, `openinghours.to`/`api.openinghours.com` — мёртвые хосты. Это и есть конкретный инженерный путь к дыре часов, а не поиск API — приоритет №8 §15.10 получает размер.
- `visitastana.kz`/QazTourism: JSON-LD SEO-спам, sitemap отдаёт 500 (второй раз подтверждено); **Яндекс Maps API §5.1.5** дословно «Сохранять, обрабатывать и видоизменять полученные через Сервисы Данные … за исключением случаев временного хранения (кэширования) результатов ответа на запросы исключительно для целей улучшения функциональности и работоспособности Сервиса» — **числового срока в прочитанной редакции нет** (не путать с HERE, где 30 дней указаны явно) ⇒ хранение запрещено, разрешён только служебный кэш; ранний вердикт §14.0 подтверждается, не пересматривается.

### 18.2 Kazakh-first: измеренный потолок (мои числа, скаут завышал)
В shipped-базе **110 из 2 294 (4.8 %) записей имеют `name:kk`**, `name:en` — 180 (7.8 %). ⚠️ **Это не 110 переводов** (разбивка по shipped-базе, `names.name:kk`): **77** содержат kk-графику `әғқңөұүһі` (4 из них — копия `name`, когда имя уже казахское: «Қазақ елі», «Олимпиада сақиналары» — легитимно), **33** — без kk-графики: точные копии брендов/русских имён («Express Doner Kebab», «The Kitchen», «Театр», «Буфетъ» с ятью) и кириллический транслит («Суши фокс», «Кофе бум», «Рибок Адидас дисконт орталыгы» — с опечаткой вместо `орталығы`); кавычки в значении есть у 8, но по парному критерию (`«`≠`»` или нечётное `"`) **реально не закрыты 2**: «Ататүрік» саябағы» (way/1460702136) и ЦОН «…бойынша Нұра" ауданының бөлім»; остальные 6 — легитимные парные кавычки в названиях ЦОН (пересчёт python-проходом по всей базе, не grep-ом первых 4 МБ). В деке говорить «казахское название — где засвидетельствовано», а не «110 переводов»: лингвист в жюри откроет пять карточек и увидит «Буфетъ». Коллектор `name:kk` **не теряет** — ключ в `KEPT_TAG_KEYS` (`collect/overpass_poi.py:164,269`), а в сыром OSM-срезе было 95 (`data/poi.osm_stats.json` `count_with_name_kk`) ⇒ узкое место — **сам OSM, а не наш пайплайн**. Каналы добора и их реальный выход:
- **Wikidata**: wdid **на уровне места** есть лишь у **76 записей** (из 127 строк с Q-id: 51 — `brand_wikidata`, т. е. сеть целиком, а не точка; в сыром OSM-срезе venue-тега и того меньше — `count_with_wikidata_tag: 29`). Прогнал по **34 ещё не покрытым** id (живой `wbgetentities props=labels|sitelinks`, сырой ответ сохранён: `recon/round8/wd_kk_labels_raw.json`): kk-имя даёт **+13** — все 13 через `labels`, `kkwiki` не добавил ни одного; прежняя «+18» была ad-hoc-прогоном без сохранения ответа и не воспроизвелась. Аудит пар по qid (18.10): **11 из 13 категорийно точны** (музей↔музей, театр↔театр, арка↔арка), 2 концертные привязки (Q573362 `Astana Musical`, Q4230441 `Концертный Зал Астана`): qid привязан к venue-тегу OSM, тождество гарантировано источником тега, но kk-метка — официальное имя зала, не торговое; в merge-пакет только после ручной сверки. **Union с `wiki_places`: 12 уникальных имён** (Q18405670/Q97168093/Q42422896 — те же сущности, что в четвёрке `wiki_places`, не считаем дважды; уникальна из четвёрки только «Нұр-Астана мешіті») ⇒ merge-пакет post-freeze: **110 → 122** (5.3 %), с двумя концертными — 124. ⚠️ Методическая ловушка, на которой попадались дважды: ключи sitelinks — **`ruwiki`/`kkwiki`**, а не `ru`/`kk`; наивный запрос даёт ложные 0 %.
- **Уже лежащий на диске канал**: `data/wiki_places.json` (55 карточек, у **33** есть kk-title в `sitelinks`). Поля `names`/`sitelinks` — обычные JSON-объекты в обоих файлах (проверено типами: `dict`); прежняя фраза «строками-repr ⇒ нужен `ast.literal_eval`» была неверна и снята. `name:kk` в обеих базах лежит **внутри словаря `names`**, а не на верхнем уровне записи; первая проверка искала `row['name:kk']` прямо и получила ложные «0 кандидатов» — это была ошибка релауна, а не опровержение. **Повторила корректно** (точное нормализованное имя, `kk` в базе у записи нет): **6 кандидатов**, и это настоящий потолок канала, а не «+8» (подстрочный джойн надувал: «Нур»-кафе → «Президенттік саябақ», «Mega»-бар → «МЕГА Астана», «Астана Арена» → «Астана Арена» с нулевым приростом). Из 6 честно проходят аудит имени **4** знаковых места: Национальный музей РК, Мечеть Нур Астана, Константино-Еленинский собор, Триумфальная арка Мангилик Ел. Ещё 2 — пересечение сущностей по имени: `Байтерек` (`restaurant`) ↔ монумент «Бәйтерек (монументі)», `Концертный Зал Астана` ↔ «Тың игерушілер сарайы» (нужен ручной verdict). ⇒ правильный ключ — **`qid`/координаты ≤150 м + аудит пары**, а не имя: чистый джойн по координатам дал **1 пару и та ложная** (ресторан `Del Papa` в 5 м от Президентского парка не есть парк). **Реальный бесплатный прирост — 4 (до 6 с аудитом) — это не 8, не 33 и не 136; трогать shipped-БД ради 4 имени не стоит до 22.10** (двигает цитируемые 4.8 %).
- **Госреестр топонимов** `s_geonims`: 3 016 улиц Астаны, но **настоящее казахское название (отличается от RU или в казахской орфографии) — 25 %** по моей выборке 2 500 строк; остальные 75 % — калька (`ЗАВОДСКАЯ`/`ЗАВОДСКАЯ`). Внутри этих 25 % есть мусор (`Көктал поселок` — казахское слово + русское «поселок»; `Париж коммунасы` в поле `name_rus` ↔ `Парижской коммуны` в `name_kaz`, т. е. поля перевёрнуты; `Шұбар ш а` — разорванный токен), ⇒ перед использованием нужен ручной аудит ~30 строк, а не только счётчик. Ценность реестра — **строка адреса** (`көш.`, `даңғ.` из `d_geonims_types`), а не название места.
- **Итог по kk — потолок низкий, теперь измерен честно.** Достоверно: в базе **110 из 2 294 (4.8 %)** `name:kk`; wdid **на уровне места** 76, из них 42 уже с kk в базе; по 34 непокрытым живой прогон даёт **+13**, из них **11** проходят qid-аудит, union с `wiki_places` = **12 уникальных** (см. выше); реестр топонимов даёт kk **адреса**, а не названия мест; `wiki_places.json` — **4 готовых к аудиту имени + 2 спорных**. Оценки «~170–200», «~300» и «110 → 136» сняты как невоспроизводимые. Кафе, фастфуд и детские площадки (1 078 записей) казахского названия в открытых данных не имеют вообще. **Community-reference по именованию** (`recon/round9/forum_wishes.md`): тред «Key "int_name" must be deprecated» (2026-03, 51 пост) и голосование Feature Proposal «Restrict int_name for exonyms» (2026-08) — живой спор о том, как хранить не-локальные имена (`name:kk` vs `int_name`); в нашей базе `int_name` не собирается (нет в `KEPT_TAG_KEYS`, `collect/overpass_poi.py`), используется `name:kk`, но при публикации правок в OSM ссылаться стоит на свежую конвенцию, а не на wiki 2012 года. Единственный масштабируемый путь — **генерация с честным происхождением**: в базе уже есть прецедент `name_generated` (473 записи) и `description_auto`, значит kk-отображаемое имя можно генерировать тем же способом, помечая `field_sources = generated`, и никогда не называть его «официальным». Формулировка для деки: «интерфейс и ответ на kk/ru/en; казахское название — где засвидетельствовано (OSM/Wikidata), иначе — генерация с пометкой».

### 18.3 Измеренный спрос вместо симуляции: потолок ниже заявленного
Скаут предложил подменить симулированный спрос просмотрами статей Википедии. Оказалось, **это уже в проде**: `collect/wiki_enrich.py:267 fetch_pageviews()` → `popularity_pageviews` (`merge.py:413`, CC0, уже учтён в `data/ATTRIBUTION.md` и `docs/licensing.md`), т. е. «новый источник» здесь — не источник, а уже работающий признак. Пересчёт по shipped-базе: статья сопоставлена у **51** POI, непустые просмотры — у **24 из 2 294 (1.0 %)**. Моя прежняя оценка «24 % из 41 названия» завышена: джойн по подстроке ловил мусор («Детская площадка», сеть `Bambino` — не про это место), а без гейта «статья именно об этом объекте» (координаты в bbox Астаны или `P131`-иерархия) число вообще невалидно, с гейтом — ещё меньше. ⇒ **ярлык «смоделированный спрос» в `docs/qa.md` снимать нельзя** — это честно и защищаемо; pageviews остаются украшением карточек знаковых мест, а не заменой слоя. Прочее: Google Trends `api/explore` — 429 (cookie-dance); daily-RSS трендов KZ — новостной шум, не POI; Flickr без ключа — «Invalid API Key»; Wordstat — только OAuth. Ресурс для роста — не добыча данных, а покрытие джойна (пул 240 элементов Wikidata → 51 сопоставленный).
**Рабочий и бесплатный сигнал спроса — автоподсказки**: `suggestqueries.google.com/complete/search?client=firefox&hl=ru&gl=kz&q=куда сходить` → 200, реальные формулировки «куда сходить в астане **с детьми**», «…**сегодня**», «…**бесплатно**», «что посмотреть в астане **за 1 день**»; `hl=kk` через Yandex `suggest-ff.cgi` отдаёт **настоящие казахские** фразы («астанада қайда баруға болады»), тогда как Google `hl=kk` на кириллице даёт русскую выдачу. Лицензии на строку нет; robots не запрещает ⇒ **разово собрать ~100 формулировок вручную и использовать как eval-корпус** (это закрывает известную слабость: 2 казахских кейса), в ранк-тайм не гонять.

### 18.7 Продуктовые допущения → цитируемые нормы (скаут `scout8_assumptions.md`; ключевое подтвердила основная нить)
- **Скорость 4.5 км/ч перестала быть выдумкой.** Мета-анализ Murtagh et al. (35 исследований, 14 015 взрослых), дословно: *«Usual / Comfortable pace: 1.31 m/s (95% CI: 1.27–1.35 m/s), or 4.57 – 4.86 km/h»* ⇒ наше 4.5 — нижняя граница опубликованного интервала. **Зимний коэффициент тоже опубликован**: Ryeng (Норвегия, естественный эксперимент, n=1 551) — уплотнённый снег −6.5 %, рыхлый −8.5 %, посыпанный лёд −9.8 %, **гладкий лёд −17 %**; Comeau (Toronto, n=3 114) −15.9 % на снегу ⇒ формулировка для слайда: «4.7 км/ч (мета-анализ) × зимняя поправка 0.85–0.95 (Ryeng/Comeau) = 4.5». Возраст: Bohannon & Williams — плато 1.30–1.43 м/с в 20–59 лет, 4.1–4.5 км/ч в 70–79 ⇒ для «медленного» профиля нужен отдельный коэффициент, а не смена глобальной константы.
- **Лимит «с ребёнком ≤ 15 мин»: норма РК есть, но наш лимит МЯГЧЕ её (в ~2 раза)**: СН РК 3.01-01-2013 «Градостроительство…» (действующий, изм. 30.04.2025, prg.kz doc_id=36077358) — детский сад ≤ **300 м**, школа ≤ **500 м** пешком ⇒ по нормативу это ≈9 мин до школы с детуром, а наш лимит 15 мин = `kids_walk_radius_m()` = 865 м по прямой / ≈1125 м с дорогой — намеренно **выше** школьного (иначе отсекались бы легальные дальние площадки, как и написано в `docs/scenarios.md`); «15-минутный город» генплана — про доступность услуг, не про предельный лимит, подпирать им константу нельзя; для дошкольника норматив жёстче, ужесточение под пресет — после 22.10. Менять константу НЕЛЬЗЯ: `h2-03` ожидает `max_walk_min_one_way: 15`.
- **PM2.5 > 35 — не наша цифра, а казахский норматив**: Приказ МЗ РК № ҚР ДСМ-70 от 02.08.2022 «Гигиенические нормативы…» (проверено: hspc.kz отдаёт 200 на приказ) — **ПДК среднесуточная (с.с.) PM2.5 = 0.035 мг/м³ = 35 мкг/м³**; у того же норматива ПДК максимально-разовая (м.р.) = 0.16 мг/м³ = 160 (наш порог — именно с.с. = 35, не м.р.). ⚠️ Ранее здесь была ошибка в индексе («м.р. = 35»), исправлена по строке приказа. Для контраста: руководство ВОЗ 2021 строже (суточная 15 мкг/м³, годовая 5) ⇒ если брать ВОЗ, порог сработает чаще — это продуктовый выбор, а не факт.
- **Мороз**: по казахстанским критериям опасное явление — **−35 °C и ниже**; отмена занятий в школах Астаны −25…−29 °C при ветре 2–4 м/с (Казгидромет/Управление образования); канадская шкала Wind Chill (ECCC): −28…−39 = «кожа открытая замерзает за 10–30 мин». Наш порог «не идти дальше 600 м» при ощущаемой ≤ −15 °C — **мягче всех трёх нормативов**, т. е. консервативен, но цитируемого основания ровно на −15 нет ⇒ оставляем как допущение и измеряем на своём логе.
- **Резерв 60 мин на аэропорт**: FlyArystan публикует «стойки регистрации открываются за 2 ч и закрываются за **40 минут** до вылета» (скаут получил 200; моя прямая прогонка URL дала 404 — страница на SPA-хостинге, **цитату не перепроверяла**, в слайд ставить только после ручной сверки). Станция LRT «Әуежай» — 50–100 м до внутренних / 250–350 м до международных ⇒ 60 мин = закрытие стоек (40) + очередь + пеший участок; обоснованно, но считать надо от конкретного терминала.
- **Доступность**: госреестр **inva.gov.kz** (МТСЗН РК) — по Астане план 1 595 объектов, адаптировано > 1 450; СП РК 3.06-101-2012 — уклон пандуса ≤ **1:12 (8 %)**, ширина 1.0–1.2 м. При этом OSM-потолок подтверждён (352 узла `wheelchair`, `tactile_paving` = **4**), а исследования качества OSM-тегов (Mobasheri, Heidelberg) дают <5–10 % микроатрибутов на путях ⇒ **полноценный why-routing в Астане невозможен в принципе**, и это число, а не оправдание.
- **Ничего хранимого о посещаемости «сейчас» не существует**: у Places API (New) нет поля Popular Times (issue годами открыт), Foursquare `hours_popular` есть, но на PAYG кэширование запрещено, а на Enterprise — только 24 ч кэш ⇒ dwell-time остаётся нашей метрикой из лога, а не покупным данным.
- **Циркуити 1.25/1.3 — внешней нормы нет; ОТКАЛИБРИРОВАН ВНУТРЕННЕ, допущение опровергнуто по направлению** (`recon/round10/detour_dedup.json` — ЕДИНЫЙ корпус: OD-ячейки ~110 м дедуп, фильтр hav(концов)≥150: 233 Valhalla-ноги → 192 ноги в **148 независимых ячейках**, декод штатной `decode_polyline6`; петлистость считается на ячейках, est/real — на ногах того же корпуса, других корпусов в реестре больше нет): петлистость медиана **1.42** (p25 1.289 / p75 1.67 / p90 2.183 / **max по медианам ячеек 5.23**; в том же корпусе на уровне ОДНОЙ ноги max 6.26 = нога 1237 м при 198 м между концами, реальный U-обход барьера, не снаппинг — числа различаются уровнем агрегации, не фильтром) Оговорка уровня (19.10): это **петлистость, измеренная нашим роутером Valhalla**, а не истина в последней инстанции — движок несёт открытый 21 месяц баг #4419 «пешеход не может сойти с тротуара» (нет топологии sidewalk↔crossing), и max-ячейка 198→1237 м — ровно его симптом: хвост распределения вероятно НАДУТ роутером. Для деки: 1.42 = «наблюдение роутера», консервативность допущения 1.25 от этого только выигрывает (реальная петля ≤ измеренной); прод и так ходит прямой ×1.25 без Valhalla против допущенных 1.25 ⇒ **поисковый радиус щедр ~14 %** и ROUTED_SLACK перестаёт накрывать от p75. Отображаемые МИНУТЫ при этом почти не ошибаются, но без гарантии: поножная пара `est=(1.25·hav)/75` против Valhalla `s/60` (безразмерное, n=192) даёт **медиану 0.97, IQR 0.82–1.07** — занижение дистанции и завышение темпа в константах компенсируются в среднем до −3 %, хвосты по перцентильной шкале: p25 −18 %, p90 +14 %, max +41 % — временной гарантии это не даёт (в деку ссылаться на перцентили detour_dedup.json, не на «±20 %»). Прежняя формулировка отозвана: «минуты занижены ~12 %» — это дистанционная цифра. Вторая константа — допущение РОУТЕРА: Valhalla считает s = m / фиксированные ~5.0 км/ч (per-leg ratio IQR .09–.12 — нулевой человеческий разброс), наши 75 м/мин консервативнее его 83; «перекалибровать на 83» значит заменить одно допущение другим. Внешней нормы по-прежнему нет: самокалибровка нормой не называется, «3 из 7 cite norms» не меняется. Выборка ноги ≥100 м (walking.py:7).

**Итог раунда 8 по направлению:** «мы ничего не выдумываем» теперь применимо к 3 из 7 допущений с дословными источниками (скорость — мета-анализ, PM2.5 — приказ МЗ РК, доступность — инва.gov.kz + СП РК); дистанции с ребёнком — допущение, ограниченное СН РК только по смыслу («школа ≤500 м»), наш лимит мягче нормы в ~2 раза — так и говорить, и честно «допущение» к остальным трём. Это ровно то, о чём спрашивает жюри-аналитик из `strategy.md`.

### 20.7 Транспортный слой остановок: имена для kk-пользователя теряются на сборке (мера shipped-данных + один Overpass-запрос, 18.10, `recon/round10/bus_stops_probe.json`)
Транзитный слой `data/mobility/stops.json` (183 записи, потребитель `app/walks/mobility.py:159`) показывает пользователю **только романизированные имена**: «Ministerstvo oborony», «Detskii sad Karlygash», «ZhK Ekspo-Plaza» — kk-графики нет ни в `name`, ни в `tags` (0/183), кириллицы тоже 0. Причина найдена в коде и подтверждена живым тестом (18.10): `stops_query()` (`collect/mobility/stops.py:72`) ищет остановки внутри `area(1520)` с комментарием «Q1520 = Astana», но в Overpass `area(<число>)` — это **area id, не QID**, а `area(1520)` в ответ на `out tags` вернул **0 элементов — такая площадь не существует вообще** ⇒ селектор детерминированно пуст, зеркало ни при чём; `stops_stats.json` честно зафиксировал итог: `osm_stops_raw: 0, with_osm: 0, gtfs_only: 183`. Правка post-22.10 одной строкой: `area["wikidata"="Q1520"]` (рабочая форма мерена в §19.4 — 953 lit-way), иначе re-run вернёт те же 0; параллельно — `name:kk` в whitelist `:152-156`. (GTFS-Zenodo-имена — транслит из GPS-датасета, авторы его романизировали сами; см. также поставку в двух числах за разные области (это НЕ перекрёстная валидация одного и того же): 948 узлов по площади Q1520 (`recon/round4/scout4_transit.md:20`, 17.10, текст селектора в артефакте не сохранён) и 879 по прямоугольнику bbox (мой запрос 18.10) — разницу 948↔879 объясняет геометрия (админ-граница против bbox), для плана берётся диапазон 879–948).
Поставка тем временем есть: **879 `highway=bus_stop`-узлов в bbox города** (пересъёмка 18.10; тот же тег `highway=bus_stop`, но ДРУГОЙ селектор — bbox-координатами, тогда как `stops.py:74` ищет внутри мёртвой `area(1520)`), а в POI-базе лежат 29 OSM-платформ, из которых **13 (45 %) несут kk-графику** («Атамекен», «Есиль», «Астана Арена»…). **Joinability не измерена** (поправка к этому же вечера): тест «1/183 ≤60 м» гонялся против 29 транзит-POI базы — это платформы LRT («Аэропорт», «Есиль»), другой слой, его результат про автобусный джойн не говорит ничего. Правильная мерка появится только после re-run коллектора: сколько из 183 GTFS-точек находят `bus_stop`-узел из 879 в ≤30 м.
Продуктовый вывод (post-22.10, в деку как план): «перезапуск коллектора принесёт kk-имена бесплатно» — **опровергнуто мерой 18.10**: `name:kk` имеют лишь **23 из 879 узлов (2.6 %)** (`recon/round10/bus_stops_probe.json`, `bg_66`; `name` вообще у 508), а коллектор и так выбрасывает kk на входе — `_osm_stops:145` берёт `name` или `name:ru`, whitelist `:152-156` = highway/public_transport/bus/shelter. Честная цепочка фикса: (0) `area["wikidata"="Q1520"]` вместо `area(1520)` (`:72`), (1) сохранять `name:kk` + языковый фолбэк в `station_name` (белый список `:152-156`), (2) ≤30м-джойн GTFS↔OSM после re-run, (3) realizing потолок kk-покрытия — 23 узла ⇒ настоящие 856 безымянных-в-kk платформ = очередь OSM-разметки (тот же two-way сюжет, что §20.6). Романизация 183 имён — свойство источника (GTFS-Zenodo `stop_name` транслитом; декод cp1251 в `:113` при чём только для иных полей).
