# scout4 gov (GovOpenData) — structured payload

## summary
Swept KZ gov/municipal registries machine-first. Two genuinely new machine endpoints found on data.egov.kz that bypass the known api/v4 key wall: `GET /datasets/getdatasetsre` (+`/getdatasetsrecount`) — keyless JSON enumeration of the whole catalogue (3944 published datasets; Astana akimat = exactly 52, all slugs dumped) — and `GET /datasets/exportjson?index=&from=&count=` WITHOUT a `version=` param (with version= it returns `[]`, which is why previous rounds saw nothing). Result: the akimat's registries are name+address+phone only; ONE of the 52 carries opening hours in structured form (№730 спорт объекты, режим работы 08:30-18:00); ZERO of the 52 carry coordinates. Beaches/toilets/rinks/green-space/hotel/monument registers for Astana do not exist on the portal at all (0 hits). Licence: no CC licence is attached to any KZ dataset; the only reuse rule is definitional, quoted verbatim below. Non-egov wins: gov4c.kz (ЦОН) publishes a server-rendered per-branch table for Astana with per-day opening hours (14 rows) — storable; legalacts.egov.kz exposes akimat draft acts as downloadable .docx including transit-tariff decisions (prices); Ministry of Tourism's quasi-gov tree on egov contains the museum-reserves/restoration enterprise that own heritage data. Dead: kgd.gov.kz + portal.kgd.gov.kz (DNS), astana.gov.kz / smart.astana.kz (DNS), e.astana.kz (conn refused), api.stat.gov.kz Xlsfv3 (SPA shell), old.stat.gov.kz/api (403), adilet.zan.kz for `read` (JS-only; use zakon.uchet.kz mirror), qaztourism.kz (no registry, SPA corporate site), visitastana-style akimat subdomains.

## architecture
Routing model for this thread: (1) data.egov.kz is now fully machine-reachable WITHOUT a key through the undocumented front-end endpoints /datasets/getdatasetsre(count) + /datasets/exportjson (no version) + /datasets/getmeta — that is the whole registry-discovery + snapshot path, and it is the only KZ gov source where a dataset can be enumerated, described and downloaded in one JSON round-trip. The key-gated /api/v4 path buys exactly one thing: Geoposition/latitude-longitude, which the akimat's own uploads almost never populate, so the key is worth requesting (free, /profile/apikeylist) but is NOT the blocker — the publishers simply do not enter coordinates. (2) Ownership of the POI facts we want is fragmented: akimat departments own sport/culture/health/education lists (hours for sport only, addresses everywhere, no geodata); the Ministry of Tourism's quasi-state children (museum-reserves, Қазқайтажаңарту, Central Museum, libraries) own their own 1–4 datasets each; heritage-monument registers exist only as regional initiatives (Turkistan). So the plan is per-department harvesting from a single endpoint family, not one national registry. (3) Anything schedule/hours-shaped that the akimat does not model in a dataset is published as prose on its own site — hence gov4c.kz (ЦОН branch tables) and legalacts.egov.kz .docx attachments (tariffs, seasonal object lists) are the two non-egov storable channels; both are plain HTML/file, no JS rendering, so a static fetcher suffices. (4) Official statistics (stat.gov.kz / statdata.kz / old.stat.gov.kz API) has no free machine tier at all: counts for tourism/hospitality are a paid 9-day state service, so treat as CONTRACT and do not architect a poller for it. (5) Coordinates for Astana POI therefore stay a geocoding problem (Nominatim/OSM + our own bbox join on address strings), not an open-data gap we can close by finding one more registry.
