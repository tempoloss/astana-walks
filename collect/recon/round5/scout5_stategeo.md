## Wins
1. **`openmap:roads_l` = 7 400 named Astana street centerlines with `Fees: NONE`** — the first state layer we can STORE that has street names *with geometry*; the `str_name` values (`просп. Кабанбай Батыра`) also double as a free street-name normalisation table. This is the licensed piece the brief asked for in item 4 (street lines: yes; address points: **no**, 0 such layers on map.gov.kz).
2. **`openmap:buildings_a` = 154 111 Astana building polygons** — beats our expectations for the state portal (round 1 said "buildings/roads/admin only"); still no address/cadastral attribute, so it is *background + geometry*, not geocoding.
3. **RCA (data.egov.kz) is the definitive fresh address gazetteer for Astana**: 85 256 building rows / 3 016 streets / 4 032 toponyms, typed by an 85-row RU+KK dictionary, historical city names (`Акмолинская→Целиноград→Акмола→Астана→Нур-Султан`) included for free as aliases, `max(modified)=2026-10-15`, keyless. **Replaces the ≤2017 unlicensed OpenAddresses snapshot for names/hierarchy**, keeping only its coordinate role to OpenAddresses/OSM.
4. **Exact-city slicing recipe proven** (`terms` on the 6 district `s_ats_id`s, ids as strings) + the parent's `match` approximation is now known to be biased: `match астана` type-11 = 3014 vs exact = 3016, because the match pulls other regions' «улица Астана» (verified: `", улица Астана"`, s_ats_id 202868/103668/99978).

6. **KPSSU/address GeocodeServer forward-geocodes Astana street+house** (score 83) — a second keyless runtime geocoder where Loc_address only worked in reverse.

## ЕГКН × building-polygons join verdict: **NOT usable**
- ЕГКН Astana CSV schema (verbatim from Magda dcat): `building_id, data_reg, address, type, func_z, document, kd_number` — **no lat/lon, no WKT, no geometry column**; the file is a rights register, not a spatial dataset.
- The only polygon candidate on the state geoportal, `openmap:buildings_a`, exposes `fireresist, levels, usage, material, mat1, title, addr_str, addr_num, area, id, string, temp, label, stl_code, prop, height` — **no cadastral number**, and `addr_str`/`addr_num` were `null` in the sampled Astana buildings, so there is no key (either `kd_number` or address) to join on from either side.
- Address-side resolution test failed on the OSM path: `nominatim.openstreetmap.org/search?q=улица Кумашыта 10, Астана` → **`[]`** (HTTP 200, empty) — Astana house-number coverage in OSM is not there yet, so geocoding ЕГКН addresses through OSM loses most rows. (Overpass street+house test not run: blocked by the MinIO TLS failure + request budget.)
- What *is* joinable and better: **`kd_number` ↔ `s_buildings.cadastre_number`** and **`s_buildings.s_geonim_id` → `s_geonims` street name → `openmap:roads_l.str_name`**. That chain (RCA as the spine, ЕГКН as the attribute/func_z enrichment, openmap vectors as geometry) is the recommended pipeline — but the geometry still has to be produced by geocoding (KPSSU/address, score ~83) or by the cadastral map (`map.gov4c.kz`, unverifiable from this host).
- Still to run locally (`curl -k`): row count of `2026Q3_Astana_EKGN_LANDPLOTS.csv` (13.7 MB), 5 sample `address` strings, and 3 street+house hits against Overpass `addr:street/addr:housenumber` in Astana.
